本文件是可直接交给开发代理或项目团队执行的改造指令。生成本文件不代表下列改造已经实现。新的范围包括内部包名与协议标识迁移，替代此前仅修改产品入口文案的范围。

用户提供的 Logo 参考已随文档保存：`docs/enterprise/assets/crrc-logo-reference.png`。前端已生成纯路径 SVG 草稿 `web/public/crrc-changchun-logo.svg` 和 `web/public/crrc-changchun-mark.svg`；它们由 PNG 描摹，未嵌入位图或使用字体，但不是企业官方矢量源稿，仍需品牌责任人审核确认。

## 使用方法

复制下面的总控提示词启动任务。按阶段依赖执行，每阶段形成可审查提交、验收证据和交接记录。需要多人并行时，先确定接口契约、目录负责人和集成顺序。

```text
你是 crrc_dbChat 企业内部 ChatDB 平台的技术负责人。请基于现有仓库完成全面改造，并交付团队可以持续协同开发、可构建、可部署、可验收的项目。

2. 平台服务单企业、多部门，生产环境完全离线内网。认证、组织目录、模型、embedding、reranker、数据库、对象/向量存储和审计均在内网。开发阶段批准的依赖导入与生产运行的外网访问必须分开控制。

7. 必须保留适用许可证要求的版权、许可与第三方归属文字，将其集中到 LICENSE、NOTICE 和第三方清单。不得伪造原创归属。该目录允许保留法定归属标识；除这一明确例外，产品及自有运行代码的原项目标识必须清零。已有 Git 历史作为溯源记录保留，不将改名理解为重写或抹除历史。

二、开始前先核实当前状态

读取 AGENTS.md（若有）、docs/learnProject.md、docs/enterprise/ 下的方案、启动说明和已有代码。核对 Git 分支、未提交改动、容器、卷、镜像和实际静态资源来源。
当前已知情况仅作为检查线索：已有组织同步快照/校验预留模块；已有本地源码运行镜像；前端曾仍在使用旧静态产物；本机模型服务尚未完成接入。必须通过当前文件和运行状态确认，不能照抄历史结论。
保留用户改动和业务数据，不重新初始化仓库、不重新复制整个项目、不创建递归嵌套副本、不覆盖正在使用的数据卷。

三、制定标识迁移规范并执行完整迁移

采用以下统一命名，不在过程中随意更换：
- 产品展示名、仓库名：crrc_dbChat。
- Python 根命名空间：crrc_dbchat；服务、扩展、应用、客户端和沙箱分别为 crrc_dbchat_serve、crrc_dbchat_ext、crrc_dbchat_app、crrc_dbchat_client、crrc_dbchat_sandbox。
- Python/Node 发布包、容器及服务名：使用 crrc-dbchat 前缀和合法的小写连字符形式。
- 环境变量：CRRC_DBCHAT_ 前缀。
- CLI：crrc-dbchat。
- 自有类/类型中的旧品牌前缀统一为 CrrcDbChat；资源协议、浏览器存储键和内部注册键制定一对一映射。

先输出标识清单与迁移映射，再按模块修改。检查 DB-GPT、DB_GPT、DBGPT、dbgpt、db-gpt、db_gpt 及大小写、复数、路径、编码和组合变体；原项目组织名、域名、徽章、Logo 和图形标识同样盘点。
范围必须覆盖目录/文件名、Python import/export、包分发元数据、入口点、锁文件、反射字符串、序列化 type_cls、工作流节点注册、插件发现、模板、数据库表/字段/默认值、环境变量、模型/服务注册键、API 资源标识、浏览器缓存/cookie、文件 URL 协议、镜像标签、Compose 项目/网络/卷引用、文档站、示例、脚本、测试及最终制品。
不要盲目替换第三方依赖名称或外部服务协议。属于不可修改外部契约的项列出证据、迁移选择与验收影响，不伪造不存在的包、域名或 API。

对持久化状态单独设计迁移：
- 先备份并在副本演练，识别历史 Flow JSON、类路径、模型配置、组织映射、文件记录、会话、缓存和数据卷。
- 提供幂等的离线迁移工具，记录版本与摘要；明确旧值到新值的映射、失败中止、恢复方法和可逆边界。
- 历史标识映射放入独立迁移交付物，不让永久运行代码依赖旧命名空间。若过渡兼容层必要，必须列出期限、移除条件及其尚未满足清零的事实。
- 不因 Compose 项目或卷改名而启动空库、丢失原数据或误报迁移成功；旧卷的归属映射必须经过核对。
- 不在没有备份和明确授权的情况下直接迁移真实生产数据。

四、前端品牌与实际构建链

建立统一 brand 配置，集中维护产品名、企业名、颜色、Logo 与应用图标；移除重复硬编码。
替换登录、侧栏展开/收起、移动端、浏览器 favicon、页面 title/meta、分享页、导出报告、空状态、错误页、文档站和加载页的原品牌。用户上传的是 Logo 参考图，不表示要求替换业务分析图表组件。
制作标准、深色背景适配和小尺寸图标资产，保证路径矢量、无外网引用、无字体依赖及无内嵌位图；不要拉伸或裁掉 CRRC 字标。
从 web 源码安装锁定依赖、完成生产构建，并把新产物纳入实际运行镜像。禁止直接修改压缩后的 JS 来替代可复现构建。
运行制品应记录 Git commit、前端构建版本、镜像摘要和依赖来源；确认服务返回的是本次构建文件。浏览器清空缓存后检查桌面、移动端、深链接、暗色主题、Logo 和标题。源码改了但页面仍显示旧品牌即验收失败。

每个关键函数说明：作用、调用前提、主要参数和返回值、权限与 workspace 范围、异常、外部副作用及事务/幂等要求。适用时解释算法选择、分支原因、取消与重试行为。
中文 docstring/JSDoc 放在函数定义处；复杂分支补中文行内注释。不得改变对外 schema 描述或工具参数语义而不验证调用兼容。
记录“已审阅并有有效中文说明 / 缺失 / 生成代码或第三方排除”清单。中文字符计数仅用于初筛，人工或独立代码审查核对说明与实现是否一致。不要给依赖包和生成产物批量插入无意义注释。

六、组织同步与企业边界

在已有预留模块上核对契约，实现可替换的内网目录适配器、平台持久化边界和明确的启用配置；缺真实目录时提供测试适配器，生产默认禁用模拟目录。
同步覆盖组织树、部门、用户、成员关系、启停状态、稳定外部 ID、完整/增量快照与游标。校验空/重复 ID、未知引用、树环、自引用、跨组织父子关系以及批次重复。
持久化同步必须具备预览、受控提交、幂等批次、事务、失败回滚和脱敏审计。账号停用及部门变更应传播至授权/缓存/任务上下文；同步不能自动授予管理员权限。
认证、RequestContext、workspace/资源 ACL、SQL 执行策略、工具隔离和审计应按依赖阶段实现。组织存在或前端隐藏菜单不构成后端授权。
工作流保存、不可变版本、审批、发布和执行记录应分离；运行绑定已发布版本，反射加载限制为批准节点。不能把多个 Web 进程等同于分布式 DAG 执行。
语义指标应有版本、公式、维度、粒度、过滤条件、单位、来源和负责人；回答能追溯指标版本、SQL 或知识引用。

七、团队协作工程

建立 CONTRIBUTING、开发环境说明、模块目录地图、架构决策记录 ADR、API/事件/数据契约、迁移规范、中文注释规范、提交与发布约定。
提供团队本地启动脚本、无真实凭据的配置模板、固定工具链和依赖锁文件，明确 Windows 开发与 Linux 运行的差异。
按认证组织、Agent/工具、工作流、RAG/语义、模型、前端、部署运维划定目录负责人和代码评审边界。CODEOWNERS 必须使用真实确认的团队账号；未提供账号时交付映射模板并标记待配置，不编造成员。
采用主干保护、短期功能分支、PR 审查与小批次合并；命名空间迁移先形成可构建基线，再让各模块并行开发。共享 schema/锁文件/迁移序号由集成人协调，避免多人覆盖同一文件。
CI 至少包括锁文件一致性、格式/静态类型、关键单元与集成测试、前端构建、旧标识扫描、关键函数注释检查、依赖/凭据扫描与镜像构建。
本地能够实现的配置直接提交；GitHub 分支保护、审批团队和内网制品库等需要真实管理员权限的配置，列明实际状态，不宣称模板等于生效。
交付模块任务卡：范围、负责人角色、输入/输出契约、依赖、验收用例、回退方法、PR 合并顺序和交接记录。

八、阶段与交付顺序

P0：完成现状审计、原标识清单、迁移映射、模块依赖图、关键函数清单和测试基线。
P1：迁移包/目录/import/入口点/配置/注册标识，修复反射与序列化引用；交付可安装、可导入、可启动的工程基线及历史数据迁移工具。
P2：统一前端品牌和 CRRC 矢量资产，完成从 web 源码到运行镜像的构建与浏览器验证。
P3：按关键链路补充中文说明，同时完善组织同步及企业身份/权限契约；对行为变化执行对应测试。
P4：按既有企业方案实现授权隔离、工作流治理、语义问数、工具控制和离线模型接入，按依赖逐个交付业务闭环。
P5：完善团队开发规范、CI、契约、评审及发布机制；其中可独立的文档和 CI 工作可提前开展。
P6：用全新环境和真实内网资源完成验收，输出安装包、SBOM、版本清单、备份恢复/升级回退文档和团队交接材料。
每个阶段持续执行必要检查。发现缺依赖或已有缺陷时修复或给出准确阻塞证据，不把剩余需求删掉来缩小验收范围。

九、验收标准与证据

1. 标识：自有运行源码、产品资源、构建产物和实际页面中旧品牌/命名空间零命中。法律归属文件与独立历史迁移交付物使用逐文件、逐原因白名单，不能通过忽略整个 packages、web、docs 或 static 目录使扫描虚假通过。
2. 基线功能：从干净检出完成 Python 安装与 CLI 启动、前端构建、服务启动；模型适配、Agent 工具链、工作流创建/保存/执行、文档入库/检索、语义问数分别有真实请求和结果证据。
3. 历史兼容：旧工作流、数据库资源、会话、文件和存储引用在副本迁移后可读取/执行；验证幂等重跑和失败恢复。
4. 注释：关键函数清单全部完成有效中文说明，并抽查权限、事务与调用链描述；未覆盖项必须显式列出。
5. 品牌：浏览器实际加载新 SVG 与当前静态构建，所有品牌入口一致，清缓存/刷新/深链接后仍成立。
6. 组织与权限：重复同步、用户停用、组织树非法关系、跨部门访问、旧入口绕过和撤权场景有通过证据。
7. 离线：空缓存且禁止公网时仍可安装获批离线制品并启动；模型缺失明确失败，无下载或云端 fallback。没有真实本地模型不得以占位响应证明模型功能通过。
8. 协作：另一名开发者可依据文档完成环境启动、分支开发、必要检查、PR 和版本发布；远端保护设置以平台实际配置为准。
9. 运行：健康检查仅证明基础服务就绪。分别报告页面、API、模型推理、embedding、检索、工作流、组织同步的可用状态，不能以首页 200 证明全功能验收。

十、执行与汇报规则

在已授权范围内持续执行，不反复询问同一权限；先阅读当前源码再修改。不得暴露真实凭据、删除用户数据、伪造测试通过或把待实现项写成已有能力。
每阶段提交：实际变更、关键调用链、迁移步骤、运行制品版本、已执行验证及证据、未完成项及原因、下一阶段依赖。最终提供项目团队可直接接手的完整交接文档。
对指定远端提交本次授权范围内的代码与文档，推送后核对本地/远端提交号。所有功能和制品通过相应验收后才宣称整体完成。
现在从 P0 开始，先核实当前仓库与运行状态，形成可执行任务清单，再连续推进上述阶段。
```
